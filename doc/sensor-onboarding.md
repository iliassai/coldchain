# Sensor onboarding and local environment setup

This guide records the sensor setup for the current Django implementation and is maintained with `feat/cold-chain-backend-v1`. Until that implementation branch is merged into `master`, switch to it before following the commands below.

## IDs and credentials

There are three different identifiers in this flow:

- **Sensor UUID** identifies the `Sensor` row in Django and is the argument to the provisioning command.
- **Sensor credential** is printed once as `<credential-uuid>.<secret>`. The server stores only a hash of the secret. The credential UUID selects the credential record; the secret proves possession.
- **Sample ID** is generated by the ESP8266 for each reading and sent as `Idempotency-Key`. Firmware retries reuse the same ID so a single reading is not stored twice. You do not need to create sample IDs manually.

Do not use a sensor UUID by itself as the credential. Do not commit the full credential, Wi-Fi password, or `secrets.h`.

## Fresh local checkout

Clone the project and select the implementation branch while the backend is still there:

```bash
git clone git@github.com:iliassai/coldchain.git
cd coldchain
git switch feat/cold-chain-backend-v1
```

Set up Python using one of the repository's documented methods. With mise and uv:

```bash
mise install
mise exec -- uv pip install -r requirements.txt
```

Create local settings, load them, and initialize the new database:

```bash
cp .env.example .env
# Edit .env: set DJANGO_SECRET_KEY and DJANGO_ALLOWED_HOSTS.
set -a
source .env
set +a
python manage.py migrate
python manage.py createsuperuser
```

The current implementation uses `db-v2.sqlite3`. A fresh clone does not include the local database or `.env`; each environment must create its own database and secrets. Do not point this implementation at the old `db.sqlite3` prototype database: it has the old user schema and no automatic migration/import path for its `Dht11` rows.

## Register a refrigerator and sensor

Start Django so the admin can be used:

```bash
python manage.py runserver
```

Open `http://127.0.0.1:8000/admin/`, sign in with the superuser, and create:

1. A **Refrigerator** with a descriptive name and location.
2. A **Sensor** attached to that refrigerator, with a descriptive name.
3. A global or refrigerator-specific **Threshold policy** with the agreed temperature bounds.

The firmware credential is bound to one sensor. Create one Sensor record per physical device; do not share a credential between devices.

## Issue a device credential

Find the sensor UUID in Django admin: open the sensor record and copy the UUID from its change-page URL. Then, from the project root with the environment loaded, run:

```bash
SENSOR_UUID="paste-the-sensor-uuid-from-admin"
python manage.py issue_sensor_credential "$SENSOR_UUID"
```

Capture the command's standard output securely. It is the complete value to put in firmware, in `<credential-uuid>.<secret>` format. The secret cannot be read back from the database. Issuing a new credential revokes the previous active credential for that sensor, so only issue again when provisioning or intentionally rotating it. Update the device's `secrets.h` and upload the firmware after rotation.

## Configure and upload the ESP8266 firmware

In `firmware/esp8266-dht11/`, copy the example header and edit the local copy:

```bash
cp secrets.example.h secrets.h
```

Set `WIFI_SSID`, `WIFI_PASSWORD`, `SENSOR_CREDENTIAL`, and `SERVER_URL` in `secrets.h`. For a local Django server, use the host computer's LAN IP, for example `http://192.168.1.20:8000/api/post`; `localhost` and `127.0.0.1` on the ESP8266 refer to the board itself. Set `DJANGO_ALLOWED_HOSTS` in `.env` to accept the host/IP used by Django and restart the server with LAN access:

```bash
python manage.py runserver 0.0.0.0:8000
```

Use HTTP only on a trusted private development network. The local sketch uses plain HTTP. Do not expose Django's development server to the internet. Open `esp8266-dht11.ino` in Arduino IDE, install/select the ESP8266 board core and DHT library, choose the board and serial port, then upload. Open Serial Monitor at **115200 baud**.

The normal sample interval is 20 minutes. For a short local smoke test only, temporarily change `SAMPLE_INTERVAL_MS` in the sketch to `10000UL`, upload, verify, and restore the 20-minute value before leaving the device running. Keep `ENABLE_TEMP_TEST_OFFSETS` false for normal monitoring.

## Verify ingestion

Watch the serial output. A successful request reports an HTTP 2xx status (`201` for a new reading; `200` for an idempotent replay) and `Reading accepted`. Then open Django admin → **Monitoring → Measurements** and confirm the new row is associated with the expected sensor/refrigerator.

The firmware creates a sample ID from a per-boot nonce and an increasing counter. If a request times out, it retries the pending reading with the same `Idempotency-Key`; after a board reboot, a not-yet-accepted pending reading is not persisted in firmware RAM and may be lost.

If the serial output reports an error:

- Wi-Fi connection failure: check SSID/password and 2.4 GHz network support.
- Connection failure / negative HTTP status: check the PC's LAN IP, same Wi-Fi/LAN, server bind address, firewall, and `DJANGO_ALLOWED_HOSTS`.
- HTTP 401/403: verify the full current credential and that its sensor and refrigerator are active. Reissuing a credential revokes the previous one.
- HTTP 400: inspect the response body and payload; ensure a valid temperature/humidity reading and non-empty idempotency key.

## Adding another sensor or cloning to another environment

For another physical sensor in the same environment, create a separate Sensor row, issue a credential for that sensor UUID, and put that full credential in that board's own ignored `secrets.h` before upload.

For a fresh environment or database, repeat the local setup and admin registration steps. UUIDs and credentials belong to records in one database; the old environment's credential will not authenticate against a fresh database. Generate and provision a new credential for the new Sensor row. Keep the Wi-Fi and credential files separate per board/environment.

If a device credential is lost or exposed, issue a new one for that sensor and re-upload the firmware. Treat the old value as revoked. The raw credential cannot be recovered from Django.
